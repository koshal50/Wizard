# What Wizard Really Is

Wizard is not a code analyzer.

Wizard is not a repository scanner.

Wizard is not a wrapper around an LLM.

Wizard is not a collection of hardcoded rules.

Wizard is an autonomous repository investigation platform.

The goal of Wizard is to allow intelligent agents to safely explore unknown repositories, build beliefs about them, verify those beliefs using evidence, continuously improve their understanding, and generate trustworthy conclusions.

The central idea is that understanding should emerge from evidence and verification, not assumptions.

# Observation System

Everything begins with observations.

An observation is a fact collected from the repository or execution environment.

Examples:

* File contents.
* Folder structure.
* Configuration files.
* Runtime outputs.
* Command results.
* Error messages.
* Dependency information.
* Execution traces.

Observations are the raw material of understanding.

---

# Observation Reliability

Not all observations are equally trustworthy.

Example:

README claims:

```text
Run npm start
```

This is only a declaration.

It may be wrong.

Example:

```text
npm start
Exit Code = 0
```

This is an empirical observation.

It happened in reality.

Therefore Wizard assigns reliability to observations.

Observation classes:

## Empirical

Directly measured.

Highest reliability.

Examples:

* Execution result.
* Runtime output.
* Exit codes.

## Declarative

Repository claims something.

Medium or low reliability.

Examples:

* Documentation.
* Comments.
* Configuration labels.

## Derived

Generated by reasoning over other observations.

Reliability inherited from supporting observations.

---

# Claim System

Observations alone are not enough.

Wizard converts observations into structured claims.

Claims are things Wizard believes about the repository.

Examples:

* Entrypoint exists.
* Runtime exists.
* Dependency exists.
* Deployment method exists.
* Architecture pattern exists.

Claims are not free text.

Claims follow a schema.

This makes them computable.

---

# Claim Schema

Claims belong to registered claim types.

Examples:

* ENTRYPOINT
* RUNTIME
* DEPENDENCY
* CONFIGURATION
* ARCHITECTURE
* DATA_FLOW
* DEPLOYMENT

Future claim types can be added.

A claim type must satisfy:

* Has extractors.
* Has graph relationships.
* Has contradiction rules.

This prevents uncontrolled growth.

---

# Extractor Framework

One of the most important components.

Extractors convert observations into claims.

Example:

Observation:

```text
FROM node:18
```

Extractor creates:

```text
RUNTIME(node,18)
```

Observation:

```text
npm install express
```

Extractor creates:

```text
DEPENDENCY(express)
```

Extractors are not hardcoded forever.

Wizard will eventually have a dedicated extractor framework.

Extractors are versioned.

Extractors are evaluated.

Extractors gain or lose trust over time.

Poor extractors become less influential.

Reliable extractors become more influential.

---

# Claim Graph

Claims are stored inside a graph.

Claims are connected through relationships.

Example:

```text
Runtime
    ↓
Entrypoint
    ↓
Deployment
```

This allows Wizard to understand dependencies between beliefs.

The graph becomes the central knowledge structure.

Everything else operates on top of it.

---

# Trust System

Every claim has trust.

Trust answers:

```text
How much should we believe this claim?
```

Trust is never based on confidence alone.

Trust comes from evidence.

Trust considers:

* Evidence strength.
* Evidence diversity.
* Execution confirmation.
* Contradictions.

Trust is computed by the runtime.

Not self reported by the agent.

---

# Trust Propagation

Claims influence each other.

Example:

If a runtime is successfully executed:

```text
python main.py
```

Then:

* Runtime trust increases.
* Entrypoint trust increases.
* Dependency trust increases.

Trust propagates through graph relationships.

However propagation includes:

* Distance decay.
* Contradiction protection.
* Recalculation rules.

This prevents trust explosions.

---

# Contradiction System

Contradictions are first class citizens.

Example:

Belief:

```text
Repository uses PostgreSQL
```

New evidence:

```text
Repository uses MySQL
```

Contradiction created.

Wizard never silently overwrites beliefs.

Contradictions trigger:

* Re-evaluation.
* Trust recalculation.
* Investigation reopening.

---

# Contradiction Cascade

If a high trust belief becomes invalid:

```text
Runtime belief invalidated
```

Then all dependent beliefs become stale.

Example:

```text
Runtime
    ↓
Entrypoint
    ↓
Deployment
```

All downstream claims are flagged.

Trust is recalculated.

This works similarly to build systems.

---

# Memory System

Memory stores previous investigations.

Memory contains:

* Previous claims.
* Previous trust values.
* Previous observations.
* Previous conclusions.

Memory is versioned.

Nothing is overwritten.

Everything remains traceable.

---

# Goal Graph

Wizard does not investigate randomly.

Every investigation begins with goals.

Examples:

* Verify runtime.
* Verify entrypoint.
* Verify deployment.
* Verify dependencies.
* Characterize architecture.

Goals define success.

Goals determine importance.

---

# Investigation Priority System

This is one of the core intelligence mechanisms.

Question:

```text
What should be investigated next?
```

The runtime computes priorities.

Priority depends on:

* Information gain.
* Goal relevance.
* Uncertainty.
* Graph impact.

High priority items get investigated first.

---

# Exploration vs Exploitation

Wizard balances two behaviors.

## Exploitation

Investigate high value targets.

Example:

Likely entrypoints.

Likely configuration files.

Likely deployment files.

## Exploration

Investigate unexpected areas.

Example:

Ignored folders.

Rare file types.

Low confidence regions.

Exploration prevents confirmation bias.

---

# Agent Interaction

Agents never access repositories directly.

Agents interact through runtime tools.

Example:

```text
Read File
Search
Execute
Observe
Inspect
```

The runtime controls all access.

The runtime records all actions.

---

# Multi Agent Workflow

Repository Explorer Agent:

* Searches.
* Observes.
* Creates hypotheses.

Verification Agent:

* Challenges conclusions.
* Looks for contradictions.
* Evaluates trust.

Future agents can be added without changing runtime architecture.

---

# Secure Execution Environment

Repositories are considered untrusted.

Agents are considered untrusted.

Commands are considered untrusted.

Everything executes inside isolated environments.

Execution produces observations.

Execution never bypasses runtime control.

Security is enforced by the runtime.

Not by the agents.

---

# Resource Control

Every investigation has budgets.

Examples:

* Execution budget.
* Observation budget.
* Compute budget.
* Time budget.

Budgets prevent runaway investigations.

---

# Reliability Mechanisms

Runtime reliability includes:

* Circuit breakers.
* Failure clustering.
* Retry limits.
* Contradiction handling.
* Trust recalculation.
* Memory versioning.

Failures become information.

Not crashes.

---

# Knowledge Gain

Wizard tracks learning progress.

Progress includes:

* New claims discovered.
* Trust increases.
* Contradictions resolved.
* Goal completion.

This helps determine convergence.

---

# Investigation Convergence

Wizard stops when:

* Goals are satisfied.
* Knowledge gain approaches zero.
* Budgets are exhausted.

The investigation ends because understanding stabilizes.

Not because loops arbitrarily stop.

---

# Final Report

The final report is generated from the claim graph.

The report contains:

* Verified claims.
* Trust scores.
* Evidence.
* Contradictions.
* Execution history.
* Dependencies.
* Entrypoints.
* Deployment findings.
* Architectural understanding.

Every conclusion can be traced back to evidence.

Nothing appears without justification.

---

# The Most Important Principle

Wizard is fundamentally an Evidence Driven Belief System.

The runtime does not ask:

```text
What does the agent think?
```

The runtime asks:

```text
What evidence exists?

What claims were generated?

How much trust do they deserve?

What should be investigated next?

Has enough evidence been collected?
```

The agent provides reasoning.

The runtime provides truth management.

Together they create autonomous repository understanding.
